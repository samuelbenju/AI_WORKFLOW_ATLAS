## Cola, concurrencia e idempotencia

`AgentTask` registra estado AWAITING_APPROVAL → PENDING → RUNNING → COMPLETED/FAILED/CANCELLED, con scheduledAt, intentos, aprobación, token de lease y flags de cancelación. REPORT de ContentDraft se guarda en DRAFT; resultado revisado es una marca/auditoría, **no publicación o envío**.

Creación utiliza clave idempotente única y comprueba contenido/trigger: la misma clave no crea dos tareas ni permite cambiar límites. Entrada por eventos: API administrativa `/api/admin/agents/events` persiste evento como tarea con su clave; no es un webhook público ni se afirma integración automática con CMS/event bus. Programaciones `AgentSchedule` tienen intervalo/nextRunAt/estado y FK real. Cada ciclo materializa hasta 20 propuestas vencidas y avanza nextRunAt desde ahora; no reproduce una cola ilimitada de intervalos perdidos. Presupuesto inicial de propuestas programadas cero hasta aprobación humana; no se convierte en permiso de llamada automática.

Claims bajo bloqueo PostgreSQL corto serializan concurrencia/contabilidad entre procesos. Se elige trabajo debido, agente habilitado y aprobación vigente; límites global/per agente se comprueban antes de reservar. La llamada externa ocurre **fuera** de la transacción SQL. Reserva del mes UTC por agente y global, incluyendo coste consumido de intentos anteriores de esa tarea. El presupuesto de tokens se contrasta con límite conservador: bytes UTF-8 de instrucciones/datos + margen de framing/esquema, más salida máxima. No es un tokenizer oficial ni una medición de facturación, sino una cota conservadora; se rechaza un resultado de uso que exceda la reserva/cota y se mantiene su registro.

Lease de 120 segundos; llamada acotada a 30 s y consulta de cancelación periódica. Token de fencing impide que una respuesta tardía de un worker sustituido guarde resultados o duplique asientos. Deshabilitar agente solicita cancelar trabajo en curso. Cancelar PENDING/AWAITING_APPROVAL no consume; cancelar RUNNING intenta abortar la solicitud y suprime el borrador, pero no promete deshacer una llamada ya aceptada por el proveedor.

## Recuperación y consumo incierto

La marca dispatchedAt se confirma en DB **antes** de hacer I/O. Si un proceso muere antes de esa marca: lease vencida libera reserva y permite reintento con backoff hasta maxAttempts. Después de la marca: podría haber ocurrido consumo; se registra INTERRUPTED_OUTCOME_UNKNOWN/FAILED, se carga conservadoramente la reserva y **no se reintenta automáticamente**. Respuestas tardías se descartan mediante fencing.

429 explícito puede reintentarse con backoff acotado (máximo tres intentos desde el panel), manteniendo presupuesto total. Errores de autenticación/solicitud no son retry automático. Red/timeout/5xx/408 o respuesta inválida son inciertos: se conserva coste reservado como estimado, uso no confirmado y fallo visible. No se presupone idempotencia del endpoint Responses ni se reenvía un POST incierto a ciegas. No hay botón para liberar fondos desconocidos o reanudar ese mismo intento. Revisar cuenta/logs/factura del proveedor antes de decidir una nueva tarea aprobada; conservar auditoría. Los periodos viejos permanecen, no se resetean para ocultar consumo.

## Proveedor y seguridad

`AiProvider` desacoplado; OpenAiResponses usa endpoint fijo `https://api.openai.com/v1/responses`, modelos permitidos, JSON schema, store=false, background=false, tools=[] y máximo de salida. La única herramienta local se ejecuta desde código confiable antes de la llamada. El modelo no elige llamadas a shell, red, escritura, permisos, pagos o correo; cualquier salida que solicite herramientas se rechaza sin ejecutar. Instrucciones del operador y datos no amplían capacidades del worker.

Instrucción de sistema separa datos de órdenes. La defensa principal ante prompt injection son las capacidades ausentes y la allowlist, no promesas de que un prompt evite todos los ataques. Salida con Zod/cotas/patrón de posibles secretos, render como texto y DRAFT; no ejecuta HTML o enlaces. No se lee `.env`, sesiones o datos privados en herramientas/modelo. Registros contienen ID de respuesta, modelo, tokens/coste estimado, estado y error seguro; no cuerpos de autenticación, tarjetas, strings de conexión o stack traces con parámetros.

Panel/API/servicios OWNER/ADMIN, Origin/CSRF y Zod/JSON acotado. Nunca almacenar una clave API en configuración del agente o instrucciones. No hay registro público de agentes, selector de proveedor/URL desde navegador o endpoint de ejecución anónimo. Una entrada de prueba TEST_FIXTURE solo se permite en DB terminada `_test`; no hay fallback simulado por faltar clave real.
